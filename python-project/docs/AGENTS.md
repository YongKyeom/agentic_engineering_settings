# docs/ 작성 가이드

문서를 새로 쓰거나 고칠 때 따르는 규칙과 유형별 템플릿이다. "무엇이 어디에 있는가"는
[README.md](README.md)의 표가 정본이므로 여기에 반복하지 않는다.

## 공통 규칙

- **상세 스펙·현황의 정본은 한 곳에 둔다.** 다른 곳에는 요약과 링크를 남긴다.
  단, 루트 AGENTS.md의 필수 실행 규칙은 링크를 열지 않아도 지킬 수 있게 직접 요약한다.
  Python·Git·검증·위임의 핵심 규칙을 루트에 남기는 중복은 허용하며, 상세 설명·작업 이력을 반복하지 않는다.
- **깃 추적 문서에서 미추적(로컬) 문서를 언급하지 않는다.** clone한 독자에게는 존재하지 않는 참조다. 로컬 Plan·Handoff의 존재는 그 문서 자신과 대화로만 다룬다.
- 사람이 읽는 문서다. AI 문체(과장된 형용사, 불필요한 병렬 구조, "~을 통해" 남발)를 쓰지 않는다.
  `humanizer`·`writing-clearly-and-concisely` 스킬 원칙을 적용한다.
- 코드 구조를 바꾸는 커밋은 해당 폴더 README와 architecture 도식을 **같은 커밋에서** 갱신한다.
- 다른 저장소는 별도 승인 없이 탐색할 수 있다. 필요한 계약·근거는 이 저장소에도 기록해, 팀이 접근할 수 없는 외부 자료에만 의존하지 않게 한다. 다른 저장소의 수정은 탐색과 별개로 작업 범위를 따른다.
- 검증하지 못한 내용은 사실처럼 쓰지 않는다. `UNVERIFIABLE` 또는 "구현 시 확인"으로 표기한다.

## 작업 기록과 현황의 정본

| 작업 성격 | 기록 위치 | 남길 내용 |
|---|---|---|
| 범위·판정이 단순한 짧은 작업 | 기존 Handoff | 작업, 상태, 결과, 다음 조치 |
| 여러 단계·세션·에이전트가 필요한 장기 작업 | 해당 Plan | 공동 목표, 상세 스펙, 담당·경계, 완료 판정, 현황, 검증, 시행착오 |
| 장기 작업의 현재 위치 안내 | 기존 Handoff | Plan 링크, 현재 단계, 막힌 이유, 바로 다음 조치 |
| 오래 유지할 기술 결정 | ADR | 결정과 근거. Plan에서는 해당 ADR 참조 |

- 짧은 작업이 장기화되면 **계속하기 전에** 상세 내용을 기존 관련 Plan으로 옮긴다.
  관련 Plan이 없을 때만 새 Plan을 만든다. Handoff에는 요약과 링크를 남기고 세부 내용을 중복 관리하지 않는다.
- 장기 작업은 Plan만 읽어도 여러 에이전트가 같은 목표·스펙·완료 기준으로 작업할 수 있어야 한다.
  위임할 때 Plan의 해당 범위와 최신 확정을 전달하고, 워커 결과의 수용·보류·기각은 총괄이 반영한다.
- 구현·검증·리뷰·범위 변경·커밋 시점마다 기존 현황을 갱신한다. 새 결과를 긴 불릿으로 계속 덧붙이지 않는다.
- Plan에서 작은 구현 Packet과 여러 Packet을 모은 검수 묶음을 구분한다. 타깃 테스트·통합 결과는 Packet에, 전체 gate·독립 리뷰·Must-Close 마감 시점은 검수 묶음에 기록한다. 
  중간 commit과 최종 승인을 구분한다.
  세부 검증 주기는 [협업 규칙](agentic-engineering.md)을 따른다.
- 별도 Handoff 생성·인계는 **사용자가 요청할 때만** 한다. 대화가 길어졌다는 이유만으로 새 Handoff를 만들지 않는다.
  요청받은 인계 문서의 형식에는 `handoff` 스킬을 적용한다.

### 한눈에 읽히는 현황

1. 문서 상단에 갱신일, 현재 단계, 다음 조치를 먼저 쓴다. Handoff 요약은 한 화면 안에서 읽히게 한다.
2. 현재 작업은 표로, 실행할 절차는 체크리스트로 정리한다. 표의 한 행에는 작업 하나만 넣고 상세 근거는 아래 절로 연결한다.
3. 상태는 `예정 / 진행 / 대기 / 완료 / 제외`로 통일한다. `대기`에는 담당·선행 조건, `완료`에는 판정 근거를 적는다.
4. 검증 결과는 현재 표에 최신 값 하나만 둔다. 이전 수치·실패·재검증은 날짜와 검증 대상을 붙여 이력 절로 옮긴다.
5. 시행착오는 `문제 → 원인 → 채택/기각한 조치 → 결과`로 기록한다. 긴 로그·전체 hash는 근거 절에 두며 상태 표에 넣지 않는다.
6. 완료된 자체 구현, 동료 담당, 현업 회신 대기, 환경 미검증을 구분한다. 빈 체크박스만 보고 과거 작업을 다시 미완료로 판정하지 않는다.
7. 과거 문서는 당시 결과를 보존하되 현재 현황과 분리한다. 정본을 옮기면 기존 위치의 링크·상태도 함께 바꾼다.

### 장기 Plan의 현황 갱신

장기 Plan은 목표 목록에 그치지 않고 **설계·구현 패킷·현재 상태·검증·미결 계약**을 함께 관리한다. 다음 구조를 유지하고 작업할 때 해당 행을 갱신한다.

| 위치 | 필수 내용 | 갱신 시점 |
|---|---|---|
| 상단 요약 | 현재 단계·완료/잔여 범위·바로 다음 조치 | 착수·범위 변경·묶음 마감 |
| 구현 패킷 표 | ID·담당·상태·선행 조건·소유 범위·완료 판정 | 착수·통합·계약 변경·완료 판정 |
| 진행 근거 표 | 진행/대기/최근 마감 패킷의 브랜치·기준 SHA·최근 검증·차단 사유·다음 조치 | 구현·테스트·리뷰·통합·커밋 후 |
| 검수 묶음 | 포함 패킷·검수 시점·전체 gate/독립 리뷰·Must-Close 결과 | 묶음 동결·보완·마감 |
| 확인 큐·이력 | 미정 계약의 담당·차단 범위, 변경 근거와 수용·기각·이월 이유 | 새 회신·실패·설계 변경 시 |

- 범위 분류와 구현 패킷을 따로 쓰면 둘의 대응을 명시한다. 같은 작업을 중복 일정으로 관리하지 않는다.
- 상태는 위의 다섯 값을 사용한다. 검수 중은 진행, 통합/외부 계약 차단은 대기로 적고 구체적인 사유를 붙인다.
- 설계 작성 완료와 제품 구현 완료를 분리한다. 완료에는 판정 근거를, 대기에는 담당·필요 결정·재개 조건을 남긴다.
- 검증 근거에는 대상 SHA/범위·명령·exit code·실제 수치·artifact 경로를 적는다. 장문 로그와 과거 수치는 이력으로 분리하며, 후속 변경에 영향받은 PASS는 재확인 전 현재 결과로 쓰지 않는다.
- 원천 시나리오/API가 바뀌면 요구·설계·영향 패킷·Mock/fixture·테스트 기대값·시나리오 문서를 함께 대조한다. 확정/잠정 계약과 Mock/실모델/Live 완료를 구분한다.
- 마감은 필수 보완 → 관련 문서 현행화 → 총괄 최종 검증 → 커밋 순서다. Handoff에는 현재 단계·차단·다음 조치와 Plan 링크만 남기고 상세 표를 복제하지 않는다.

```markdown
## 현재 현황 (YYYY-MM-DD)

| 작업 | 담당 | 상태 | 완료 판정·근거 | 다음 조치 |
|---|---|---|---|---|
| 기능 단위 | 담당자 | 진행 | 상세 스펙/검증 절 링크 | 바로 할 일 |
```

## 도식 가이드

도식이 문장보다 빠른 곳(파이프라인, 상태 전이, 계층, 시퀀스)에는 도식을 먼저 쓴다.

| 용도 | 도구 | 비고 |
|---|---|---|
| 시스템 컨텍스트·컨테이너·컴포넌트 | Mermaid C4 (`c4-architecture` 스킬) | architecture 문서 기본 |
| 시퀀스·상태 전이·플로차트·ERD | Mermaid (`mermaid-diagrams` 스킬) | 시나리오·설계 문서 |
| 문서·docstring 안의 간단한 흐름 | ASCII 다이어그램 | 렌더러 없이 읽혀야 하는 곳 |

## 유형별 템플릿

### ADR (`decisions/`)

작성 절차·번호·supersede 규칙은 `decision-record` 스킬이, 폴더 규칙과 Scope Gate는
[decisions/AGENTS.md](decisions/AGENTS.md)가 소유한다. 6절 구성만 요약한다:

```markdown
# ADR-NNNN: <제목 — 결정을 한 줄로>
- 상태 / 결정일 / 관련 문서 링크
## 1. 배경        ← 왜 이 결정이 필요했나
## 2. 결정        ← D1, D2, … 번호 붙인 결정 표
## 3. 기각한 대안  ← 대안 | 기각 사유 표
## 4. 근거        ← 실측·실사·협의 등 검증 가능한 근거
## 5. 영향        ← 코드·문서·후속 작업에 미치는 영향, 미결 항목
## 6. 개정 이력
```

### Plan (`plan/`)

파일명 `YYYYMMDD_<slug>-plan.md`. 기본 로컬, 공유는 `docs/.gitignore` negation 수기 추가.
활성 Plan의 해당 범위를 작업 지시에 포함하고, 완료돼도 삭제하지 않는다. 공유·커밋은 사용자 지시와
기존 추적 정책을 따른다. 루트 `AGENTS.md`에는 특정 활성 Plan을 매번 추가하지 않는다.
`Source of Truth`의 디렉터리 안내는 유지하고, 실제 작업 Plan은 작업 지시나 기존 로컬 Handoff에서 찾는다.
미추적 Plan을 루트 README 등 깃 추적 문서에서 링크하지 않는다. 기존 지침의 언어는 번역 목적으로 바꾸지 않는다.

```markdown
# <제목> Plan
## 현재 현황         ← 갱신일·상태 표·다음 조치. 최신 결과만
## 목표와 완료 기준   ← 검증 가능한 판정식으로
## Non-goal          ← 이번에 하지 않는 것
## 상세 스펙·분업     ← 계약·파일 경계·의존 순서·Packet별 판정식·검수 묶음
## 검증 결과         ← 대상 버전·명령·수치·근거. Mock/Live 구분
## 시행착오·결정 이력 ← 문제·원인·수용/기각·해결 결과
## 리스크와 미결
```

### Handoff (`handoff/`)

평소에는 기존 문서를 갱신한다. 짧은 작업의 상태·결과와 장기 작업의 Plan 링크·다음 조치를 남긴다.
장기 작업의 상세 스펙·검증 로그·시행착오는 위 규칙에 따라 Plan으로 옮긴다.
사용자가 별도 인계를 요청하면 `YYYYMMDD_<topic>-handoff.md` 형식으로 작성하고 `handoff` 스킬을 적용한다.

### 시나리오 (`scenarios/`)

업무 카탈로그의 업무 단위로 작성한다. 각 문서는 구현·검수가 가능한 수준으로:

```markdown
# <업무명> 시나리오
## 진입 조건     ← 카탈로그 전제조건(보유 코드·선행 업무·권한)
## 단계별 흐름   ← 사용자 입력 → 화면·구조화 블록 → 상태 변화. 승인 횟수 명시
## code-owned 문구와 label
## 실패·중단     ← 각 실패 지점에서 사용자가 보는 것과 다음 행동
## 완료 기준     ← 시스템 반영·재조회 결과
```

### 폴더 README (`src/**/README.md`)

깃 서버에서 폴더를 열면 사람이 소스보다 먼저 보는 문서다. 소스를 열지 않아도 그 폴더를
파악할 수 있게 **자기완결로** 쓴다: 폴더의 목적, 모듈 지도(파일 | 책임 | 관련 ADR),
주요 아키텍처·로직(도식 우선), 의존 방향, 분업 경계.
`__init__.py` docstring과 내용이 겹쳐도 된다 — README는 사람의 진입점, docstring은
코드를 열었을 때의 동작 원칙이다.
